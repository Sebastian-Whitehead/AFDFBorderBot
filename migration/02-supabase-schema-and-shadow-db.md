# Step 02: Shadow DB and Supabase schema changes

**Goal:**
1. Build a local "shadow" Postgres 17 that has production's `public`, `economy` and `military` schemas and no data.
2. Write the schema changes the bot needs as one SQL file.
3. Prove the changes work on the shadow DB.

Production is **not** touched in this step, except for the read-only dump.

`economy` is dumped only because a trigger on `identities_player` inserts into `economy.accounts`. The bot adds nothing to `economy` and never calls economy functions.

**Preconditions:** step 01 committed. The user's decision D4 is "shadow DB". If it is "Supabase branch", STOP and ask the user how to provision it.

## 1. Production connection string (read-only use)

Ask the user for the Supabase **session pooler** connection string (Dashboard → Connect → Session pooler, port 5432). The direct `db.<ref>.supabase.co` host is IPv6-only and often fails on Windows. Put it in `.env.test` and never commit it:
```
SUPABASE_DUMP_URL=postgresql://postgres.rjakbhfokyjoujqlijqn:<password>@<pooler-host>:5432/postgres
```

## 2. Build the shadow DB

```bash
mkdir -p migration/shadow
source .env.test   # or export SUPABASE_DUMP_URL manually
docker run --rm postgres:17 pg_dump "$SUPABASE_DUMP_URL" --schema-only --no-owner --no-privileges \
  -n public -n economy -n military > migration/shadow/schema.sql
docker run -d --name afdf-shadow -e POSTGRES_PASSWORD=shadow -p 54329:5432 postgres:17
```

Create `migration/shadow/stubs.sql`, which stands in for Supabase objects the dump refers to:
```sql
DO $$ BEGIN
  CREATE ROLE anon; EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN
  CREATE ROLE authenticated; EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN
  CREATE ROLE service_role; EXCEPTION WHEN duplicate_object THEN NULL; END $$;
CREATE SCHEMA IF NOT EXISTS auth;
CREATE SCHEMA IF NOT EXISTS extensions;
CREATE OR REPLACE FUNCTION auth.uid() RETURNS uuid LANGUAGE sql AS 'SELECT NULL::uuid';
CREATE OR REPLACE FUNCTION auth.role() RETURNS text LANGUAGE sql AS 'SELECT NULL::text';
CREATE OR REPLACE FUNCTION auth.jwt() RETURNS jsonb LANGUAGE sql AS 'SELECT NULL::jsonb';
```
Load the stubs, then the schema:
```bash
docker exec -i afdf-shadow psql -U postgres < migration/shadow/stubs.sql
docker exec -i afdf-shadow psql -U postgres < migration/shadow/schema.sql 2> migration/shadow/restore-errors.txt
```

Read `restore-errors.txt`. The only acceptable errors are "already exists" (for example `schema "public" already exists`) and errors about roles, policies, extensions or `auth.*` objects missing from the stubs. If one of those is a missing `auth.*` function or role, add it to `stubs.sql`, then drop and recreate the container and rerun.

**STOP if** any `CREATE TABLE`, `CREATE FUNCTION`, `CREATE TRIGGER` or constraint in `economy`, `military` or `public` failed.

Add to `.env.test`:
```
TEST_SHARED_DATABASE_URL=postgresql+asyncpg://postgres:shadow@localhost:54329/postgres
```

Sanity check: `docker exec afdf-shadow psql -U postgres -c "\dt economy.*"` lists `accounts`, `transactions`, `transactions_entries` and `stocks`.

## 3. Write the SQL file (it must be idempotent: running it twice is a no-op)

### `migration/sql/001_bot_tables.sql`
Use this content. If D1 was answered differently, change the rank lists.
```sql
-- Ranks: allow UO and PRES (decision D1)
ALTER TABLE military.service_records DROP CONSTRAINT IF EXISTS service_records_current_rank_check;
ALTER TABLE military.service_records ADD CONSTRAINT service_records_current_rank_check CHECK (
  current_rank IS NULL OR current_rank = ANY (ARRAY['EN0','EN1','EN2','EN3','EN4','EN5','EN6','EN7','EN8',
  'OF0','OF1','OF2','OF3','OF4','OF5','OF6','OF7','OF8','OF9','OF10','OF11','UO','PRES']));
ALTER TABLE military.service_events DROP CONSTRAINT IF EXISTS service_events_rank_check;
ALTER TABLE military.service_events ADD CONSTRAINT service_events_rank_check CHECK (
  rank IS NULL OR rank = ANY (ARRAY['EN0','EN1','EN2','EN3','EN4','EN5','EN6','EN7','EN8',
  'OF0','OF1','OF2','OF3','OF4','OF5','OF6','OF7','OF8','OF9','OF10','OF11','UO','PRES']));

-- The bot's organization (service_records.organization_id is required)
INSERT INTO public.identities_organizations (name, organization_type)
VALUES ('AFDF-Para Raiders', 'military') ON CONFLICT (name) DO NOTHING;  -- already exists in production, so a no-op there

-- One identity per Discord / Steam account (the bot looks players up by these)
CREATE UNIQUE INDEX IF NOT EXISTS identities_player_discord_id_uniq
  ON public.identities_player (discord_id) WHERE discord_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS identities_player_steam_id_uniq
  ON public.identities_player (steam_id) WHERE steam_id IS NOT NULL;

-- Leave of absence
CREATE TABLE IF NOT EXISTS military.leave_requests (
  id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  player_identity_id bigint REFERENCES public.identities_player(id),
  discord_id         bigint NOT NULL,
  username           text   NOT NULL,
  start_date         date   NOT NULL DEFAULT current_date,
  end_date           date   NOT NULL,
  reason             text,
  status             text   NOT NULL DEFAULT 'active'
                     CHECK (status IN ('active', 'cancelled', 'expired')),
  submitted_at       timestamptz NOT NULL DEFAULT now(),
  last_modified      timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS leave_requests_one_active
  ON military.leave_requests (discord_id) WHERE status = 'active';
CREATE INDEX IF NOT EXISTS leave_requests_status_end
  ON military.leave_requests (status, end_date);
ALTER TABLE military.leave_requests ENABLE ROW LEVEL SECURITY;
```
Before the unique indexes go to production (step 09), run this read-only check against production:
```sql
SELECT discord_id, count(*) FROM public.identities_player WHERE discord_id IS NOT NULL GROUP BY 1 HAVING count(*) > 1;
SELECT steam_id,   count(*) FROM public.identities_player WHERE steam_id   IS NOT NULL GROUP BY 1 HAVING count(*) > 1;
```
**STOP if** either query returns rows.

## 4. Apply to the shadow DB (twice, to prove idempotency)

```bash
for f in migration/sql/*.sql; do docker exec -i afdf-shadow psql -U postgres -v ON_ERROR_STOP=1 < "$f"; done
for f in migration/sql/*.sql; do docker exec -i afdf-shadow psql -U postgres -v ON_ERROR_STOP=1 < "$f"; done
```

## 5. Tests: `tests/test_shadow_schema.py` (marker `db_shared`, skip if `TEST_SHARED_DATABASE_URL` unset)

Use a plain SQLAlchemy async engine on `TEST_SHARED_DATABASE_URL`. Run each test inside a transaction that is **rolled back**, so the shadow DB stays clean.

| ID | Test |
|---|---|
| SH1 | `SELECT public.fab_ensure_player_account('zz_test_p', 76561190000000001, 900000000000000001)` creates exactly one `identities_player` row. Calling it again creates no second row. |
| SH2 | A `service_records` row for that player in org `AFDF-Para Raiders` with `current_rank='PRES'` inserts OK. `current_rank='XX'` fails with a check violation. |
| SH3 | `military.leave_requests`: a second `active` row for the same `discord_id` fails with a unique violation. A second row with `status='cancelled'` is OK. |
| SH4 | Inserting a second `identities_player` with an existing `discord_id` fails with a unique violation. |
| SH5 | Exactly one `identities_organizations` row is named `AFDF-Para Raiders`. |

## Done when

- The shadow DB is built, and the SQL file was applied twice without errors.
- SH1–SH5 pass, the full suite passes, and production has no changes.
- Committed (SQL files and tests; the shadow dump is gitignored) as `migration step 02: supabase schema + shadow db`.
